# Plan

The living plan: what is in flight now, what comes next, and the open questions. Completed items are removed rather than checked off. Resolved questions are removed. Deferred work enters here at the moment of deferral.

## Now

- [ ] Retire `TwitchInteractionUE` from the JasperMozuStudioUE5 project, now that stream events reach Mikan through an HTTP trigger and leave as a script message. The plugin speaks IRC and PubSub, and Twitch decommissioned PubSub in April 2025, so its channel-points path is already dead. It is not listed in the `.uproject` and has no `Source/` or `Config/` references, but `Content/Levels/MainStageGameMode.uasset` carries a full integration: a `TwitchAuthentication` actor with chat and EventSub components, the auth and token flow, and handlers for subscribe, redeem, bits, bits badge, chat, join-game, and user id. Each handler's behavior has to land somewhere before the graph is gutted, most of it as a `MikanScriptMessagePostedEvent` case, so this is UE editor work rather than a file delete.
- [ ] UI modernization (`ui_update` branch): the MikanTrack UI treatment has landed (ImGui v1.92.9-docking, SDL2 2.30.10, the `MkGuiTheme` palette and Mochiy Pop One font, localized keys in en/ja including the descriptor-generated panel labels, and a dockable shell with a File/View menu bar and an in-app Log panel). One consequence to keep in mind: the `resources/localization` CDN manifest now lists the JSON tables, so old shipped builds fetching the deleted CSVs fall back to their bundled strings.
- [ ] Decide whether the editor wants multi-viewport docking (`ImGuiConfigFlags_ViewportsEnable`), which would let a floating panel become a real OS window on a second monitor. Deliberately left off: MikanXR runs four independent ImGui contexts over one shared GL context, and the SDL2 backend's viewport bookkeeping is the least-tested path in that setup.
- [ ] Localize the USB video setting slider labels. `GuiPanel_USBVideoSourceComponent` builds them at runtime from `k_videoSettingPropertyPrefixes` ("brightness" to "Brightness") inside a custom renderer, so they sit outside the descriptor label mechanism and still read English in every language.
- [ ] ARKit video source (`iphone` branch): pose-in-RTP streaming and the hardware/software two-tier decode landed through Phase 7; verify a live iPhone session end to end and confirm an old saved project referencing removed texture-source enum names still loads (relies on `VideoTextureNode`'s `FindEnumValue` fallback).
- [ ] ARKit marker tracking origin: the editor-side alignment landed (Align Camera solves an ARKit-world-to-stage offset from the origin marker and applies it in `notifyFrameBundleReceived`, see videosources.md). Verified on both decode tiers, including a full alignment run on the hardware tier, which is the one that actually exercises `readbackDirectColorTexture` (the direct texture is non-null there, so the readback is the only possible source of the CPU pixels every sample's detection needs). Three consecutive alignments with the phone moved between them agree on the offset to well under a millimetre, which is what confirms the per-sample composition. The `frameSeq` staleness guard is verified too: restarting the phone app dropped frameSeq from 17180 to 2, the guard logged the session change and cleared the offset, and the camera fell back to ARKit's raw origin awaiting a re-align.
	ARKit's own image tracking was tried first and does not work for this. `ARReferenceImage.validate` accepts a rendered marker, but detection never fires against a real printed sheet, tried both bare and with a white margin, while OpenCV reads that same marker instantly from the phone's own screenshot at an oblique angle. ARKit image tracking matches detailed photographs, and marker art is repetitive and nearly featureless by design. Do not re-attempt it.
	Measured side by side on one scene, a printed marker and a printed flower illustration in frame together, with `tools/aruco_pose_measure.py` for the OpenCV arm. ARKit found the flower in 0.06s and tracked it in all 2714 anchor updates, at 0.76/3.40/0.61mm jitter per axis and 6.77mm worst deviation. OpenCV read the marker in all 864 frames at 0.04/0.05/0.16mm and 0.55mm worst deviation, roughly twelve times tighter. ARKit never detected the marker at all. Two caveats on the gap: ARKit's figure is world-space so it carries world-tracking drift the camera-relative OpenCV figure does not, and the flower's printed width was assumed to be 100mm. The direction is not in doubt, the exact factor is. Note also that `validate` returned true for both targets, the one that tracked perfectly and the one that never tracked, so it predicts nothing.
- [ ] `AppStage_AlignCameraByUtilityMarker` never applies the camera intrinsics to the viewport camera either, the same gap just fixed in `AppStage_AlignCameraByOriginMarker`. Its overlay is drawn through whatever projection the viewport camera happens to hold. Untested here because it needs a VR utility-marker rig.
- [ ] Verify whether `DrawLayerNode`'s stencil mask rendering is vertically mirrored in the compositor. It draws stencil geometry into the working framebuffer through the unflipped aperture projection, which is exactly what made `DrawShapesNode` render shapes upside down, but no graph in the project connects a stencil so the bug has never been exercised. Confirm with a quad stencil placed off-centre before changing it, since a wrongly placed mask is worse than a mirrored one.
- [ ] `ShapeSelectNode` gathers every quad, box and model shape in the project rather than only those in the compositor's own scene, so a shape belonging to one scene draws into another scene's composite.
- [ ] Node editor snapshot history commits a step on nearly every mouse release while the compositor runs, because a node's live `float_defaults/time` value serializes into the graph snapshot and the commit dedup sees a changed graph. A plain click on empty canvas after an undo adds a step. Keep runtime-fed values out of the snapshot, or dedup on the persisted fields only.
- [ ] Cursor feedback in the interactive browser window: `CefDisplayHandler::OnCursorChange` fires but nothing consumes it, so the pointer stays an arrow over links and text fields. Deferred because it needs a new `IMkWindowContext::setCursor` plus an SDL system-cursor cache, and because ImGui's SDL2 backend calls `SDL_SetCursor` from `ImGui_ImplSDL2_UpdateMouseCursor` every `NewFrame` and would immediately overwrite it. - [ ] Vulkan shared texture writer hardening, gated on measuring the cost against a real client rather than the cube harness. The first pass blits the client's image into a linked D3D11 texture, waits the fence, then sends through Spout's `SendTexture` copy, so a frame costs one CPU stall and one extra GPU copy. Vulkan is the only backend that needs either: DX11 copies on the client's own device, and DX12 hands its command queue to the D3D11On12 device so the copy is queue-ordered behind the client's rendering with no stall at all. There is no Vulkan equivalent of that trick, since D3D11 cannot submit to a `VkQueue`.
	- The stall and the copy are a fork rather than two steps, because Spout's `CreateSharedDX11Texture` deliberately uses `MISC_SHARED` with a named mutex for every texture (its comment cites DX9 receiver compatibility for refusing `SHARED_KEYEDMUTEX`). A texture arbitrary receivers open therefore cannot be keyed-mutex.
		- Keyed mutex (`VK_KHR_win32_keyed_mutex`) on the private linked texture removes the CPU stall and keeps the copy. It forecloses zero-copy, since the texture stays private, and the writer must create it rather than borrowing `spoutdx.CreateSharedDX11Texture`.
		- Zero-copy sender registration through `sendernames.CreateSender` over the linked texture's own handle removes the copy and keeps the stall, since Spout's named mutex is CPU-level and says nothing about whether the Vulkan blit landed. The writer takes over the sender bookkeeping `CheckSender` does today.
		- A shared semaphore (`VK_KHR_external_semaphore_win32` imported as an `ID3D11Fence`) lets the D3D11 copy wait on the GPU without touching the texture's flags, so unlike keyed mutex it composes with zero-copy. Closest analogue to what the DX12 path gets for free.
	- Client cost differs per option, which is why link-engine comes first: zero-copy is entirely writer-side, while keyed mutex and the shared semaphore each add a device extension the client enables at `vkCreateDevice`.
	- Deferring the fence wait to the start of the next write pipelines the stall behind the client's own frame with no new extension, at one frame of added latency. Not obviously worth it for mixed-reality compositing, so it is not a free fallback.
	- RGBA16F and the shadow buffer are mapped but unverified, since the test harness requests neither.
- [ ] link-engine as a Vulkan client: the engine side of the seam the Vulkan writer proves. The engine creates its device with `VK_KHR_external_memory_win32`, hands `MikanVulkanDeviceInterface` to the client API, and each frame hands the offscreen main view image with its layout as a `MikanVulkanTexture`, which means `render.hpp` needs an export of that image without leaking a Vulkan type. Depth arrives as an `R32_SFLOAT` color image, so the engine also needs a pass writing linear depth to one.
- [ ] Single-undo object bursts: outliner cascade delete and script trigger runs. Deleting a subtree today records one transaction per object, child-first, which undoes correctly in reverse but takes N undo steps, and a script trigger such as `generate_lights` that removes and creates many objects lands the same way even though the run is bracketed as a gesture. Merging them needs `TransactionHistory` to append create and destroy ops into an open gesture instead of sealing on each (`m_pendingDestroyOp` is a single op today); verify with the `history` automation commands before keeping it.
- [ ] Scene lighting: decide whether a single global probe suffices or region-of-interest probes near the character are needed. `LightEnvironmentComponent` already carries a world position, so this needs no wire-format change. Answerable only from the end-to-end look in Unreal.
- [ ] Scene lighting: calibrate the exposure scalar automatically instead of by hand per shoot.
- [ ] Depth proxy mesh: refine residual metric scale against tracked anchors or the floor plane, so a capture needs no ArUco marker in frame.
- [ ] Depth proxy mesh: occlusion-grade silhouette edges. The current proxy is a shadow catcher; it cannot occlude a character walking behind real furniture.
- [ ] Model render geometry over HTTP: return a content-addressed, ETag-revalidated URL instead of the geometry inline, so clients cache across sessions and the transfer leaves the websocket. Reconsider if payloads outgrow the current few megabytes or a client that is not on the editor's machine needs the geometry; `ix::HttpServer` binds 127.0.0.1 only today, and `HttpInterprocessMessageServer` dispatches route handlers on the main thread, so a route serving a large body would need to answer from the cached payload without a main-thread hop.

Sharing safely needs a content hash on the wire so a depth recapture that rewrites the same path invalidates the cache, which makes it a protocol change with bindings regeneration and the schema guard.

Every module has one owner in the app, so this only bites tests today: `arkit_video_source_system_test_independent_instances` leaks both its loaders to avoid it.

- [ ] macOS and Linux port, sequencing. The rendering API is not the blocker it looks like: macOS deprecated OpenGL in 10.14 but still ships a working 4.1 core profile, and MikanXR's usage sits well under that cap. Every shader is `#version 330 core`, `SdlWindowContextManager` requests a 3.2 core context, and the only call past GL 3.3 anywhere in `src/Libraries` or `src/Editor` is one debug-only `glDebugMessageCallback`. So the existing renderer runs on macOS as-is, and the port should be proven on GL 3.3 before any backend swap is considered. Start with the headless Linux compositor, since `MikanCmd` plus `-runTests` skips CEF, ImGui, OpenVR, and the window system entirely and isolates the dependency problem below.
- [ ] Cross-platform dependency acquisition. Everything under `deps/` is a Windows binary package fetched by `InitialSetup_x64.bat`, so each needs a per-platform path. RefurekuGenerator is the hard gate: four targets run it as a pre-build step and it ships as `rfk_v2.2.1_windows.zip`, so nothing builds without it. The rest in rough order of cost: CEF (works on macOS but needs the helper-process app bundle structure), `MikanOnnx` execution provider selection (DirectML-first today, needs CoreML on macOS and CUDA or CPU on Linux), `MikanWMFVideo` (needs AVFoundation and V4L2 siblings, which the plugin module contract already accommodates), OpenVR (Valve dropped macOS, so `MikanSteamVR` is Windows and Linux only), and the Winsock leaves in `MikanDMX/UdpMulticastSocket`, `AutomationSocket`, and `LuaDebugSocket`.
- [ ] Cross-platform shared texture transport. This is what makes a port worth having, and it is Windows-only end to end: `MikanSharedTexture` is Spout2 over DirectX shared NT handles, all four writers funnel through a D3D11 texture, and `SharedTextureReader` receives into a GL texture id. macOS needs an IOSurface path and Linux needs dma-buf or opaque FD. `SharedClientGraphicsApi::Metal` already exists in the enum with nothing behind it, so the accessor seam is in the right place. Protocol-touching, so it carries the wire-protocol rules and a bindings regeneration. Independent of any renderer decision.
- [ ] `MikanRenderer` immediate-state to pipeline-state refactor. `Public/` is already free of GL types and `createMkGraphicsContext` already takes an `eGraphicsAPI` listing Vulkan and Metal, but the semantics are a GL state machine: `DrawLayerNode` mutates blend function, blend equation, and stencil op inside the draw loop against a shared state stack. Every modern API bakes that state into an immutable pipeline object, so the `mkStateSet*` calls have to become a pipeline descriptor built before the pass, and `CompositorNodeGraph` has to reorganize around explicit render passes. That refactor is a valid OpenGL design on its own, so it can land incrementally under the existing backend with the test suites verifying no functional change, which touches the 144 consumer files once instead of twice. It is the prerequisite for any backend swap, and Vulkan with MoltenVK is the front-runner if one happens, since this branch already vendored Vulkan-Headers and volk, compiles SPIR-V through `deps/dxc`, and has a working `-vk` client path. Note that the material files (`.compmat`, `.shapemat`) are a user-facing asset format (`MaterialAssetReference` exposes a `*.mat` file dialog), so any shader-language change past GLSL breaks projects that hand-author materials. Materials authored as graphs survive it: the material compiler emits through `IShaderWriter`, so the change is a second writer plus recompiling every `.graph` (materials.md). Custom expression nodes carry raw GLSL and would need rewriting by hand.
