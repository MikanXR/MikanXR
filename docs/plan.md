# Plan

The living plan: what is in flight now, what comes next, and the open questions. Completed items are removed rather than checked off. Resolved questions are removed. Deferred work enters here at the moment of deferral.

## Now
- [ ] Node editor snapshot history commits a step on nearly every mouse release while the compositor runs, because a node's live `float_defaults/time` value serializes into the graph snapshot and the commit dedup sees a changed graph. A plain click on empty canvas after an undo adds a step. Keep runtime-fed values out of the snapshot, or dedup on the persisted fields only.
- [ ] Cursor feedback in the interactive browser window: `CefDisplayHandler::OnCursorChange` fires but nothing consumes it, so the pointer stays an arrow over links and text fields. Deferred because it needs a new `IMkWindowContext::setCursor` plus an SDL system-cursor cache, and because ImGui's SDL2 backend calls `SDL_SetCursor` from `ImGui_ImplSDL2_UpdateMouseCursor` every `NewFrame` and would immediately overwrite it. Doing it means toggling `ImGuiConfigFlags_NoMouseCursorChange` on that window's io while the pointer is over the page area.

## Next

Correct while no stage carries a rotation. A rotated stage needs the UE side to rotate them by the stage actor's transform first.

Closing the window makes the identical edit apply immediately. The window owning the graph is reasonable; the silent divergence between a log line claiming a load and a render that ignores it is not. Either make the reload path take the file over the open window, or refuse the reload and say the window owns the graph.

The break is somewhere in `UMikanEngineSubsystem::OnDMXDataChanged` to `AMikanClient::HandleDMXDataChanged` to the per-actor `OnDMXDataChanged`. Masked until now because nothing ever lit up at all.

- [ ] The SDK event fetch reads into a fixed 1 KB buffer (`MikanEventManager.cpp`, `MikanEventManager.cs`) and never pops an event larger than that, so one big property update, such as a light environment's `sh_coefficients`, wedges every later event behind it. Query the size with a null buffer first and size to fit.
- [ ] The SDK event queue is unbounded, so a client that pumps slower than the editor publishes accumulates stale frame events without limit and renders further into the past as it goes.
- [ ] A free-running camera still pays the compositor's full frame event queue latency: `tryCompositeOldestFrame` waits for the queue to fill although no client renders for a specific index. Compositing at depth 1 for such a camera would cut the composite latency by the queue depth.
- [ ] The automation `component create <system> <class>` verb calls `addNewObjectByTypedDefinition` with no definition-init callback, so it builds components in states the outliner's add actions never produce: an anchor or shape with no `parent_transform_id`, a camera or light with no owner stage. `ProjectOutlinerActions` sets those at creation and is the only path a person can take. A drive that creates objects this way is therefore testing a shape of object the editor does not otherwise have, which is how the scene-less gizmo crash was found. Either give the verb an optional parent argument it passes through, or say plainly in automation.md that it is a raw constructor and a drive that wants a realistic object sets the ids itself afterwards.

- [ ] Vulkan shared texture writer hardening, gated on measuring the cost against a real client rather than the cube harness. The first pass blits the client's image into a linked D3D11 texture, waits the fence, then sends through Spout's `SendTexture` copy, so a frame costs one CPU stall and one extra GPU copy. Vulkan is the only backend that needs either: DX11 copies on the client's own device, and DX12 hands its command queue to the D3D11On12 device so the copy is queue-ordered behind the client's rendering with no stall at all. There is no Vulkan equivalent of that trick, since D3D11 cannot submit to a `VkQueue`.
	- The stall and the copy are a fork rather than two steps, because Spout's `CreateSharedDX11Texture` deliberately uses `MISC_SHARED` with a named mutex for every texture (its comment cites DX9 receiver compatibility for refusing `SHARED_KEYEDMUTEX`). A texture arbitrary receivers open therefore cannot be keyed-mutex.
		- Keyed mutex (`VK_KHR_win32_keyed_mutex`) on the private linked texture removes the CPU stall and keeps the copy. It forecloses zero-copy, since the texture stays private, and the writer must create it rather than borrowing `spoutdx.CreateSharedDX11Texture`.
		- Zero-copy sender registration through `sendernames.CreateSender` over the linked texture's own handle removes the copy and keeps the stall, since Spout's named mutex is CPU-level and says nothing about whether the Vulkan blit landed. The writer takes over the sender bookkeeping `CheckSender` does today.
		- A shared semaphore (`VK_KHR_external_semaphore_win32` imported as an `ID3D11Fence`) lets the D3D11 copy wait on the GPU without touching the texture's flags, so unlike keyed mutex it composes with zero-copy. Closest analogue to what the DX12 path gets for free.
	- Client cost differs per option, which is why link-engine comes first: zero-copy is entirely writer-side, while keyed mutex and the shared semaphore each add a device extension the client enables at `vkCreateDevice`.
	- Deferring the fence wait to the start of the next write pipelines the stall behind the client's own frame with no new extension, at one frame of added latency. Not obviously worth it for mixed-reality compositing, so it is not a free fallback.
	- RGBA16F and the shadow buffer are mapped but unverified, since the test harness requests neither.
- [ ] link-engine as a Vulkan client: the engine side of the seam the Vulkan writer proves. The engine creates its device with `VK_KHR_external_memory_win32`, hands `MikanVulkanDeviceInterface` to the client API, and each frame hands the offscreen main view image with its layout as a `MikanVulkanTexture`, which means `render.hpp` needs an export of that image without leaking a Vulkan type. Depth arrives as an `R32_SFLOAT` color image, so the engine also needs a pass writing linear depth to one.

A box or tent resolve pass on the client texture before `DrawLayerNode` samples it would make any scale look right. Worth doing if a scale other than 2x turns out to be the one a shoot wants.

- [ ] macOS and Linux port, sequencing. The rendering API is not the blocker it looks like: macOS deprecated OpenGL in 10.14 but still ships a working 4.1 core profile, and MikanXR's usage sits well under that cap. Every shader is `#version 330 core`, `SdlWindowContextManager` requests a 3.2 core context, and the only call past GL 3.3 anywhere in `src/Libraries` or `src/Editor` is one debug-only `glDebugMessageCallback`. So the existing renderer runs on macOS as-is, and the port should be proven on GL 3.3 before any backend swap is considered. Start with the headless Linux compositor, since `MikanCmd` plus `-runTests` skips CEF, ImGui, OpenVR, and the window system entirely and isolates the dependency problem below.
- [ ] Crash minidump contents: `MiniDumpWithDataSegs` is left out to keep the file attachable, and an editor dump at the main menu with libcef loaded measures 2 MB without it. Measure what data segments add before restoring them; the win is global variables being readable in the debugger.
- [ ] Cross-platform crash reports. `CrashHandler.cpp` is Windows only (the SEH filter, the CRT hooks, and the minidump writer), with an empty stub elsewhere. The port needs its POSIX branch: signal handlers writing a backtrace from a forked child, or Breakpad-format minidumps if the report is to stay one file format across platforms. Sequence it with the headless Linux compositor, since `MikanCmd -crash` is how the branch gets verified.
- [ ] Cross-platform dependency acquisition. Everything under `deps/` is a Windows binary package fetched by `InitialSetup_x64.bat`, so each needs a per-platform path. RefurekuGenerator is the hard gate: four targets run it as a pre-build step and it ships as `rfk_v2.2.1_windows.zip`, so nothing builds without it. The rest in rough order of cost: CEF (works on macOS but needs the helper-process app bundle structure), `MikanOnnx` execution provider selection (DirectML-first today, needs CoreML on macOS and CUDA or CPU on Linux), `MikanWMFVideo` (needs AVFoundation and V4L2 siblings, which the plugin module contract already accommodates), OpenVR (Valve dropped macOS, so `MikanSteamVR` is Windows and Linux only), and the Winsock leaves in `MikanDMX/UdpMulticastSocket`, `AutomationSocket`, and `LuaDebugSocket`.
- [ ] Cross-platform shared texture transport. This is what makes a port worth having, and it is Windows-only end to end: `MikanSharedTexture` is Spout2 over DirectX shared NT handles, all four writers funnel through a D3D11 texture, and `SharedTextureReader` receives into a GL texture id. macOS needs an IOSurface path and Linux needs dma-buf or opaque FD. `SharedClientGraphicsApi::Metal` already exists in the enum with nothing behind it, so the accessor seam is in the right place. Protocol-touching, so it carries the wire-protocol rules and a bindings regeneration. Independent of any renderer decision.
- [ ] `MikanRenderer` immediate-state to pipeline-state refactor. `Public/` is already free of GL types and `createMkGraphicsContext` already takes an `eGraphicsAPI` listing Vulkan and Metal, but the semantics are a GL state machine: `DrawLayerNode` mutates blend function, blend equation, and stencil op inside the draw loop against a shared state stack. Every modern API bakes that state into an immutable pipeline object, so the `mkStateSet*` calls have to become a pipeline descriptor built before the pass, and `CompositorNodeGraph` has to reorganize around explicit render passes. That refactor is a valid OpenGL design on its own, so it can land incrementally under the existing backend with the test suites verifying no functional change, which touches the 144 consumer files once instead of twice. It is the prerequisite for any backend swap, and Vulkan with MoltenVK is the front-runner if one happens, since this branch already vendored Vulkan-Headers and volk, compiles SPIR-V through `deps/dxc`, and has a working `-vk` client path. Note that the material files (`.compmat`, `.shapemat`) are a user-facing asset format (`MaterialAssetReference` exposes a `*.mat` file dialog), so any shader-language change past GLSL breaks projects that hand-author materials. Materials authored as graphs survive it: the material compiler emits through `IShaderWriter`, so the change is a second writer plus recompiling every `.graph` (materials.md). Custom expression nodes carry raw GLSL and would need rewriting by hand.
